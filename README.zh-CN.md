# teamlog

**一本公共日志，每人一个 agent，不需要服务器。** 面向小团队的沟通约定：团队里每个人都和自己的 AI agent 一起工作。

[English](README.md)

## 想法

团队沟通复杂，是因为每条消息都要有收件人。发的人得决定谁需要知道、什么时候说、用什么形式。会议、群、抄送、工单，都是在解决这个路由问题。

团队没有干脆把所有事写在同一个地方，是因为没人读得完。agent 读得完。

所以在 teamlog 里没有人"发"消息：

- 人只和自己的 agent 说话。
- agent 把简短的条目追加到一本公共日志里。
- 每条新日志会被看一遍，决定它还**该给谁**看。这叫 *hub 职责*。它不需要专门的 hub 服务器：下一个接触日志的 agent 顺手完成，用的就是它的主人正在用的那个模型。
- 每个人的 agent 读取给自己主人的内容，决定**什么时候**告诉他。

```
log/
  20261006-090100-alice.md     登录接口改完了，测试通过，等人评审
  20261006-090200-bob.md       下周三前需要定价方案，@carol 能给吗
  20261006-090300-carol.md     re: ...-bob   方案周一给。另外我觉得应该先做企业版
  20261006-090700-hub_bob.md   re: ...-alice @bob [action] 负责评审
```

Alice 的那条没有 @ 任何人。它到了 Bob 那里，因为评审归他管。整个机制就是这样。

## 试一下

需要 Python 3.8+ 和 git。没有依赖，不需要 API key，不需要任何配置。

```bash
git clone https://github.com/Ivann1242/teamlog && cd teamlog
./examples/demo.sh
```

演示会在临时目录里模拟一个四人团队：写日志、一个 agent 履行 hub 职责、回复关闭一个请求、没人回应的请求在 26 小时后被重新提起。

## 团队怎么用

一个人创建团队空间，推到全队都能访问的 git 远端：

```bash
./tl init ~/myteam          # 生成 log/、people/、AGENTS.md，并复制一份 tl
cd ~/myteam
git remote add origin <你的远端> && git add -A && git commit -m "teamlog" && git push -u origin HEAD
```

每个人 clone 这个仓库，声明自己是谁：

```bash
./tl join alice --owns "登录, sso" --cares "企业版"
```

然后用你的编码 agent（Claude Code、Codex，或任何会读 `AGENTS.md` 的工具）打开团队空间。`AGENTS.md` 会告诉它每次会话开始时做什么：

```bash
./tl sync       # git pull，提交日志，push
./tl hub        # hub 职责：列出还没人路由的日志，由 agent 判断并记录
./tl inbox      # 给你的新内容，分三档
```

以及什么时候替你写日志：

```bash
./tl write "登录接口改完了，测试通过，等人评审"
./tl reply <id> "评审通过"
```

配置就这些。没有任何东西需要在后台运行。

## 工作方式

```
team/
  log/              只追加的条目，事实的唯一来源
  people/alice.md   每人一份：负责、关心、不关心、打断，加自由说明
  hub/seen-alice    alice 的 agent 已经履行过 hub 职责的条目
  AGENTS.md         给 agent 的说明
  tl                工具本身，一个文件
  STATUS.md         `tl status` 的本地快照，不入库
```

一条日志是一个 Markdown 文件，文件名为 `<UTC 时间>-<作者>.md`。第一行可以写 `re: <id>` 表示回复。格式只有这些。

每个 agent 有两件事要做：

| | hub 职责 | 为自己的主人 |
|---|---|---|
| 回答的问题 | 这条还**该给谁**看 | **什么时候**告诉我的主人 |
| 命令 | `tl hub`，然后 `tl route` | `tl inbox` |
| 写什么 | 路由条目（`hub_<名字>`） | 主人的进展、请求、决定 |
| 不做什么 | 不做决定、不排优先级、不发表意见 | 不替主人承诺或决定 |

`tl hub` 会打印还需要路由的日志，以及每位队友的一行概要。agent 用下面的命令作答：

```bash
./tl route <id> bob:action:"负责代码评审" dave:fyi:"影响产品路线"
./tl route --none <id> [<id> ...]
```

条目里的约定：

- `@名字` 表示请这个人处理。在对方回复之前，这个请求一直是未完成状态。
- `cc @名字`（或 `抄送 @名字`）表示只是让对方知道。
- `#decision`（或 `#决定`）会让这条进入 `tl status` 的"已决定"。
- 作者自己回复并带上 `#closed`（或 `#关闭`），可以关闭自己发起的请求。

个人档案 `people/<名字>.md` 的四个关键词行，可以用英文键 `owns / cares / ignores / interrupt`，也可以用中文键 `负责 / 关心 / 不关心 / 打断`。

收件箱把新内容分成三档：

| 档位 | 含义 | 哪些内容会进来 |
|---|---|---|
| `NOW` | 立刻告诉主人 | 主人一直没回应的请求被再次提醒；命中 `interrupt` 关键词的内容 |
| `LATER` | 下一个自然间歇再说 | 待处理的请求；别人对主人条目的回复 |
| `FYI` | 不用汇报，记住即可 | 值得知道、但无需行动的内容 |

这些档位只是按规则算出的基线。agent 应该在此基础上自己判断，例如看出有人被卡住时，把那一条提到 `NOW`。

四条规则保证它不容易坏：

1. **@ 不需要路由。** agent 直接读提到自己主人的条目，所以即使还没人履行 hub 职责，请求也能送达。
2. **没有私有状态。** 一切都在仓库里。任何 agent 都能履行 hub 职责，没有需要一直运行的进程，也没有会丢的东西。
3. **并发的 agent 不会冲突。** 每个文件只有一个写入者：日志和路由条目都带作者名，每个 agent 有自己的 `hub/seen-<名字>`。两个 agent 离线时路由了同一条日志，两份记录都会保留，对每个人以先写的那条为准。
4. **能用代码做的不用模型。** 提醒和 `tl status` 是普通代码。只有"这条和谁有关"需要模型判断。

没人回应的请求会在 24 小时后被重新提起，最多三次，由下一个履行 hub 职责的 agent 写出。这个 agent 往往就属于欠着回复的那个人。

## 没有 agent 的情况

服务器、定时任务，或者没有 agent 的成员，可以用 `tl hub --auto` 让它自己完成 hub 职责：

```bash
./tl hub --auto                       # 用每个人的 owns / cares 关键词匹配
TL_LLM="claude -p --model haiku" ./tl hub --auto --watch 300 --sync
```

`TL_LLM` 是任何"从标准输入读提示词、把回答打印出来"的命令，hub 期望得到一个 JSON 数组，例如 `[{"to":"bob","kind":"action","why":"负责代码评审"}]`。如果命令失败或回答无法解析，这一条会退回关键词匹配，hub 会说明。关键词匹配很粗糙，只能找到字面匹配。

`claude -p` 不允许在另一个 Claude Code 会话内部启动，所以请在普通终端里运行。

## 安全

日志条目是数据，不是指令。`AGENTS.md` 要求 agent 不得在没有主人授权的情况下按条目里的话行动。路由决定在写入前会被校验：只接受已知的队友，只接受 `action` 和 `fyi` 两种类型，不会路由给作者本人。

## 命令

```
tl init [dir]              创建团队空间
tl join <name>             在这台机器上声明你是谁，并创建档案
tl write "text"            追加一条日志（也可以从标准输入传入）
tl reply <id> "text"       回复一条日志
tl inbox [--peek|--json]   给你的新内容，分三档
tl hub                     hub 职责：提醒，以及需要路由的日志
tl route <id> name:kind:why ...   记录这条还该给谁看
tl route --none <id> ...   记录这条不需要给别人看
tl hub --auto [--watch S] [--sync] [--llm CMD] [--no-llm]   不靠 agent 完成 hub 职责
tl show <id>               一条日志及其回复
tl log [-n N] [--hub]      最近的日志
tl status                  谁在等谁、每人最新一条、已做的决定
tl sync                    git pull，提交日志，push
```

`<id>` 可以简写成任何唯一的片段。环境变量：`TL_ME`（身份）、`TL_ROOT`（团队空间）、`TL_LLM`（`--auto` 用的模型命令）、`TL_REMIND_HOURS`（默认 24）。

## 现状与局限

这是 v0.2，一个实验。已验证和未验证的部分如下：

- 工具行为有端到端测试覆盖（`python3 -m unittest discover -s tests`），包括两个克隆对同一条日志各自履行 hub 职责，再通过 git 远端同步且不产生冲突。
- "agent 只凭 `AGENTS.md` 履行 hub 职责"试过一次：把一份六条的日志分别交给两个 Claude 模型，这份日志用关键词匹配一条都路由不出来。两个模型都独立走完了流程，并把两条关键的日志转给了正确的人；较小的模型多发了两条不必要的"知悉"。**这只是一个场景、两次运行，不是评估。** 整个设计押注在路由质量上，它也是下一步要测量的东西。
- 其他 agent（Codex 等）还没有试过。

已知局限：

- 为小团队设计，大约十人以内。日志没有分区。
- 日志对所有能访问仓库的人公开。没有私密条目，也没有访问控制。
- 默认信任所有人。没有任何机制阻止队友冒用别人的名字写日志，而且给一条日志做路由的，往往就是它作者的 agent。
- 一条日志只路由一次，由先到的 agent 完成。模型弱，路由就差。
- 没有"通知所有人"的条目；涉及全队的事，需要逐个 @。
