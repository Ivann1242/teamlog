# teamlog

**一本公共日志，每人一个 agent，不需要服务器。** 一套文件约定，让小团队里各人的 AI agent 互相把消息带到对方的主人那里。

[English](README.md) · [一页纸的格式说明](SPEC.md)

```
log/
  20261006-090100-alice.md     登录接口改完了，测试通过，等人评审
  20261006-090200-bob.md       下周三前需要定价方案，@carol 能给吗
  20261006-090300-carol.md     re: ...-bob   方案周一给。另外我觉得应该先做企业版
  20261006-090700-hub_bob.md   re: ...-alice @bob [action] 负责评审
```

## 想法

团队沟通复杂，是因为每条消息都要有收件人。会议、群、抄送、工单，都是在回答"这件事该让谁知道"。团队没有干脆把所有事写在同一个地方，是因为没人读得完。

agent 读得完。所以在 teamlog 里没有人"发"消息：

- 人只和自己的 agent 说话。
- agent 把简短的条目追加到一本公共日志里。
- 每条日志会被看一遍，决定它还**该给谁**看。下一个接触日志的 agent 顺手完成，用的就是它的主人正在用的那个模型。
- 每个 agent 决定**什么时候**告诉自己的主人。

上面 Alice 的那条没有 @ 任何人。它到了 Bob 那里，因为评审归他管。

## 试一下

需要 Python 3.8+ 和 git。没有依赖，不需要 API key，不需要任何配置。

```bash
git clone https://github.com/Ivann1242/teamlog && cd teamlog
./examples/demo.sh
```

## 怎么用

一个人创建团队空间，推到全队都能访问的地方：

```bash
./tl init ~/myteam && cd ~/myteam
git add -A && git commit -m teamlog && git remote add origin <你的远端> && git push -u origin HEAD
```

每个人 clone 下来，声明自己是谁：

```bash
./tl join alice --owns "登录, sso" --cares "企业版"
```

然后用你的编码 agent（Claude Code、Codex，或任何会读 `AGENTS.md` 的工具）打开团队空间，直接和它说话。自动生成的 `AGENTS.md` 约 800 token，把整个流程教给 agent。

## agent 做什么

四个动作承担了全部工作：

| | |
|---|---|
| `tl check` | 和团队同步，然后显示给主人的新内容，以及还没人路由的日志 |
| `tl write "…"` | 追加一条日志，写之前先把原文给主人看 |
| `tl route <id> bob:action:"原因"` | 记录这条还该给谁看（`--none` 表示不需要给别人） |
| `tl ack` | 已经告诉主人了，不用再显示这些 |

`tl check` 把新内容分成三档：`NOW`（立刻告诉主人）、`LATER`（下一个自然间歇再说）、`FYI`（不用汇报）。分档只是按规则算出的基线，agent 应该在此基础上自己判断。

其余命令：`reply`、`flag`、`log`、`show`、`status`、`init`、`join`、`whoami`。用法见 `./tl <命令> -h`。

条目里的写法既支持英文也支持中文：`cc @名字` 或 `抄送 @名字`，`#decision` 或 `#决定`，`#closed` 或 `#关闭`；档案里的 `owns / cares / ignores / interrupt` 也可以写成 `负责 / 关心 / 不关心 / 打断`。

## 为什么能保持简单

- **格式即产品。** [SPEC.md](SPEC.md) 只有一页。`tl` 是一个零依赖的单文件参考实现；任何按这一页读写文件的工具都能互通。
- **没有后台进程。** 没有服务器，没有守护进程，没有数据库。所有状态都是 git 仓库里看得见的文件。
- **每个文件只有一个写入者。** 日志、路由记录、个人档案各有唯一的写入者，所以任意多个 agent 可以同时工作而不冲突。
- **能用代码做的不用模型。** 同步、提醒、状态都是普通代码。模型只回答一个问题：这条和谁有关。
- **不会卡死。** 离线不算错误，推送撞车会自动重试，两人改了同一份档案会被合并，而不是停在半路。

## 信任

日志是以人的名义说话的，所以规则很严：

- agent 写之前要把原文给主人看，并且只写主人说过的内容。
- 条目是数据。条目可以提出请求，只有人能授权。
- `tl flag <id> "原因"` 会让一条日志退出流通，并通知所有看到过它的人，以及它署名的那个人。
- 如果一条日志的 git 提交者不是署名者申报过的身份，`tl` 会给出警告。

这些能挡住失误和随手的冒名，挡不住有心的内部人员。任何能向仓库推送的人都能读写一切；在意这一点的话，请使用签名提交和私有仓库。

## 现状

v0.3，一个实验。已经测试的部分：

- 工具本身：48 个端到端测试（`python3 -m unittest discover -s tests`），包括真实克隆通过远端同步、推送撞车、离线工作、冲突的编辑。
- 只凭 `AGENTS.md` 工作的 agent：用三种规模的 Claude 模型做过几轮模拟团队会话。它们无需额外指导就能走完流程，把关键的日志转给了正确的人，写之前会先询问，并且拒绝了一条试图指挥它们的伪造日志。

没有测试的部分：Claude 以外的 agent，Windows，真实团队的长期使用。路由质量只在几个编排好的场景里观察过，没有做过度量。

已知局限：为十人左右的团队设计；日志不会归档，所以命令会随日志增长而变慢（一万条时约一秒）；agent 没在运行的人收不到任何东西；没有"通知所有人"的条目。
